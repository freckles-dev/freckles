# freckles — Vision

> **Superseded where they diverge:** [design.md](design.md) (2026-08-21) is
> the current model — DAG of named nodes, outcome-hashed operations,
> content-addressed store. Its §1 lists exactly which concepts of this
> document it replaces (pipeline/stages, transformer, artifact, lockfile,
> journal, tool store). This document remains valid for motivation, the
> curation philosophy (deferred, not dropped), and the reproducibility
> stance.

freckles is a Python framework for minimum-configuration, reproducible
devops. The user writes the smallest configuration that cannot be defaulted —
which applications to enable, a root domain, IP addresses, secrets — and
freckles combines it with a curated catalog of infrastructure units to
produce, through a declarative pipeline of stages, first fully rendered
deployment artifacts and then a running system. Every rendered artifact is
content-addressed: the same configuration and the same catalog always produce
the same output, and freckles can always say which configuration a deployed
system corresponds to.

This document describes the idea in full. It is the precursor to a formal
specification (see [Roadmap to the spec](#roadmap-to-the-spec)).

## 1. Motivation

Self-hosted infrastructure suffers from configuration sprawl. Every tool in a
modern stack — a VM provisioner, an OS installer, a GitOps operator, a secrets
scheme, per-application Helm values — exposes its own configuration surface,
and most of what an operator writes into those surfaces is not a decision but
a repetition: the same "use this storage class", "wire the database like
this", "expose it on the private ingress" choices, restated per app, per tool,
per cluster. The actual decisions — which apps, which host, which domain,
which secrets — are a tiny fraction of the text.

[rosekube](../../rosekube/) was the experiment that made this concrete. It is
a Copier template that renders a complete single-cluster repository (Proxmox
VM via OpenTofu, Talos Linux, Flux, sops/age secrets, Tailscale, Longhorn)
from roughly twenty-five answers — cluster name, IPs, VM sizing, a git URL.
Its app catalog encodes curation decisions once, centrally: chart versions are
pinned exactly; apps that need PostgreSQL get an app-local CloudNativePG
`Cluster` rather than a chart-bundled database, because the catalog has
decided that CloudNativePG is how PostgreSQL is done; ingress is private
(Tailscale) by default and public only by explicit opt-in.

Rosekube also exposed the limits of the template approach:

- **Hybrid ownership.** The generated repository mixes template-owned files
  (regenerated by `copier update`) with user-owned files (protected by a
  hand-maintained `_skip_if_exists` list that must enumerate every
  user-editable file of every app). The boundary is fragile, grows linearly
  with the catalog, and means the repository as a whole is never a pure
  function of its inputs.
- **One hard-coded transformer.** Copier is the only way to get from
  configuration to output. Some units would be better produced by a script, a
  package-manager invocation, or another generator entirely.
- **No reproducibility guarantees.** Nothing records which template version,
  tool versions, and answers produced a given repository, or whether the
  running cluster still corresponds to it.
- **Manual state transitions.** The journey from rendered repo to running
  cluster is a sequence of `just` recipes whose ordering and preconditions
  live in documentation and shell scripts, not in anything a machine can
  reason about.

freckles keeps what worked — the curated catalog, the minimal question
surface, the opinionated defaults — and replaces the template mechanics with
a general, pure, hashed pipeline model. Rosekube becomes the first catalog.

## 2. Core idea

> A **curated catalog** supplies infrastructure units with defaults that make
> sense in the catalog's wider context. A **minimal user configuration**
> supplies only what cannot be defaulted. A **declarative pipeline of
> stages** — each stage produced from the previous one by a pluggable
> **transformer** — turns configuration into rendered artifacts and rendered
> artifacts into a running system. Everything rendered is **content-
> addressed**, and every execution against the real world is **journaled** by
> hash, so the whole journey is reproducible and auditable end to end.

The design is inspired by Nix — pure derivations, content addressing,
lockfiles — but deliberately stops short of Nix's rigor where the cost
outweighs the benefit, and it must run on any Linux distribution without root
privileges.

## 3. Concepts and terminology

These terms are used throughout the rest of the document and will seed the
specification's glossary.

**Frecklet.** The unit of the catalog: one application or one piece of
infrastructure (an app like Paperless-ngx, an add-on like the Tailscale
operator, or a foundation like "a Talos cluster on Proxmox"). A frecklet
declares its configuration schema (which values are required, which are
defaulted), its dependencies on other frecklets, the pipeline stages it
contributes, and the pinned tools it needs. A frecklet's defaults are not
generic upstream defaults — they are the catalog's opinions.

**Catalog.** A git repository of frecklets plus the curation policies that
bind them together. A catalog is the unit of trust and of versioning: user
configurations name catalogs pinned by git ref, and a lockfile records the
exact commit. Multiple catalogs can be layered — an official catalog under a
personal overlay catalog — with later layers overriding earlier ones.

**Curation policy.** A catalog-level decision that individual frecklets defer
to. "Applications that need PostgreSQL use CloudNativePG app-local clusters."
"Ingress is private by default; public exposure is explicit." "Chart versions
are pinned exactly, never ranges." Policies are what make a catalog more than
a pile of templates: a frecklet written for the catalog inherits sensible
behavior it never had to state.

**User configuration.** The single input the user owns: which catalogs (and
refs), which frecklets to enable, and the values that cannot be defaulted —
names, addresses, domains, sizing, secrets. It is a small, declarative file
set, and it is the only thing a user ever edits. Everything downstream is
derived.

**Stage.** One node in the pipeline from configuration to running system.
A stage has declared inputs (the user configuration, outputs of earlier
stages), a transformer that produces its output, and a kind: *render* or
*execute* (see [The pipeline model](#4-the-pipeline-model)).

**Transformer.** A plugin that knows how to produce one stage's output from
its inputs. Each transformer type has an alias that frecklets refer to —
`copier` (render a Copier template), `uv-python` (run a Python script with
inline uv metadata), `pixi` (run a task in a pinned pixi environment),
`command` (run a pinned external tool) — plus transformer-specific
configuration. Transformers are versioned, and their versions are part of the
hash of what they produce. New transformer types can be added without
touching the core.

**Artifact.** The output of a render stage: a file tree (for example, a
complete cluster repository). Artifacts are immutable and content-addressed —
stored and referenced by the hash of their content — and never hand-edited.

**Lockfile.** The record that makes a run reproducible: exact catalog
commits, exact transformer versions, exact tool versions. A user
configuration plus its lockfile is sufficient to re-derive every artifact
bit-for-bit (within the [accepted gaps](#5-reproducibility-stance)).

**Tool store.** A per-user, root-free store of pinned external tools
(`tofu`, `talosctl`, `flux`, `sops`, `copier`, ...) that freckles provisions
itself. Frecklets and transformers declare tool dependencies with exact
versions; the resolved versions go into the lockfile and the hash.

**Journal.** An append-only record of executions: which artifact hash was
executed by which execute stage, when, and with what result. The journal is
what lets freckles answer "is the live system current with configuration X?"
without owning the tools' own state.

## 4. The pipeline model

A freckles run evaluates a directed acyclic graph of stages. The graph is not
hand-written by the user: it is assembled from the stage declarations of the
enabled frecklets and the catalog, given the user configuration. Frecklets
declare, declaratively, how to get from one step of the journey to the next;
freckles orders and connects those declarations.

Stages come in two kinds, and the boundary between them is the central design
line of the system:

**Render stages are pure.** A render stage is a function from hashed inputs
to a hashed artifact. Its inputs are: the user configuration, the catalog
content (pinned by the lockfile), the outputs of earlier render stages, the
transformer (pinned version), and the pinned tools it runs. Given identical
inputs, a render stage must produce identical output — this is a contract
transformers must uphold (no timestamps, no environment leakage, no
network access outside declared fetches). Because render stages are pure,
their results are cacheable: if the input hash is unchanged, the artifact is
reused, not rebuilt.

**Execute stages are effectful checkpoints.** An execute stage takes a
rendered, hashed artifact and applies it to the real world: `tofu apply`,
bootstrapping Talos, `flux bootstrap`, pushing a repository to a git remote.
Execute stages are not pure and are never implicit — each is an explicit
checkpoint that the user (or an explicitly granted automation) confirms.
Every run of an execute stage is recorded in the journal with the artifact
hash it consumed and the outcome. State produced by the underlying tools
(OpenTofu state, kubeconfigs, Talos configs) remains owned and managed by
those tools; freckles records *that* and *what* was applied, not the tools'
internal state.

The hash of an artifact therefore covers, transitively:

- the user configuration (including encrypted secret values — see
  [Secrets](#6-secrets)),
- the exact catalog commits from the lockfile,
- the transformer and its version,
- the pinned versions of every tool the stage runs,
- the hashes of all upstream artifacts it consumed.

Change any of these and the artifact hash changes; change none of them and
freckles can prove the artifact is current without rebuilding it. This also
gives day-2 operations a clean shape: editing the user configuration or
bumping a catalog ref re-renders (cheaply, thanks to caching) exactly the
artifacts whose inputs changed, and the diff between the old and new artifact
hashes tells the user precisely which execute stages need to re-run.

## 5. Reproducibility stance

freckles is inspired by Nix but is explicitly not Nix. The goal is
*practical* reproducibility — same config + same lockfile ⇒ same artifacts,
and a truthful record of what was applied — not bit-for-bit hermeticity of
the entire toolchain down to libc. Accepted gaps, stated honestly:

- **Binary tool provenance.** Tools in the tool store are fetched as upstream
  release binaries, pinned by version and verified by checksum where
  available — not built from source in a sandbox.
- **Underlying tools' network behavior.** An execute stage like `tofu apply`
  or Flux reconciliation fetches providers, charts, and images at apply time.
  The catalog mitigates this by pinning exact versions everywhere (a rosekube
  policy freckles inherits), but freckles does not proxy or snapshot those
  fetches.
- **Live-system drift.** The journal records what was applied, not what the
  system has become. Detecting drift is the underlying tools' job (`tofu
  plan`, Flux reconciliation); freckles only answers "does what we last
  applied match configuration X?".
- **Host environment.** Render purity is a transformer contract and enforced
  pragmatically (controlled environment variables, isolated working
  directories), not by kernel-level sandboxing. A hostile transformer can
  cheat; a correct one won't.

Where a gap can later be narrowed cheaply (checksum databases for tools,
optional sandboxed rendering), the design leaves room, but no gap blocks v1.

## 6. Secrets

Secrets are ordinary inputs that happen to be encrypted. The model
generalizes rosekube's sops/age flow:

- Secret values live in the user configuration, encrypted with
  [sops](https://github.com/getsops/sops) and an
  [age](https://github.com/FiloSottile/age) key. Only the value fields are
  encrypted, so structure and names stay readable in diffs.
- Because the encrypted bytes are stable, secrets hash like any other input
  and land — still encrypted — in rendered artifacts. Artifacts are therefore
  self-contained and safe to commit or publish.
- Decryption happens only at execution time, by the executing side: in the
  rosekube catalog, Flux decrypts sops secrets in-cluster; an execute stage
  that itself needs a plaintext value (an API token for `tofu apply`)
  decrypts it in memory at the moment of use, never into an artifact.
- Rotating a secret changes its ciphertext, which changes the input hash,
  which marks the affected artifacts and execute stages as stale — secret
  rotation flows through the same mechanism as any other change.

Render stages never see plaintext secrets. That single rule keeps the pure
side of the pipeline trivially safe to cache, store, and share.

## 7. Toolchain provisioning

freckles must run on any Linux distribution without root, so it cannot
assume, or ask a package manager for, its tools. Instead:

- Frecklets and transformers declare their external tool dependencies with
  exact versions (`opentofu 1.x.y`, `talosctl vA.B.C`, `sops`, `copier`, ...).
- freckles resolves the full tool set for a run, records it in the lockfile,
  and downloads anything missing into a per-user tool store (under
  `~/.local/share/freckles/tools/` or similar) — no root, no global state,
  multiple versions side by side.
- Stages run with only their declared tools on `PATH`, at exactly the pinned
  versions. Tool versions are hash inputs, so a tool bump re-renders what
  depends on it — silently different tool versions can never produce
  identically-addressed artifacts.
- Root is never required by freckles itself. Where a *target* operation
  genuinely needs elevated privileges (rare; e.g. some hypervisor-side
  setup), the frecklet must declare it, and it is an explicit, optional,
  user-confirmed part of an execute stage — never a silent `sudo`.

This mirrors what pixi/mise/uv do for developer environments, applied to the
devops toolchain, with the addition that the resolved versions participate in
the reproducibility hash.

## 8. Catalogs: distribution, versioning, layering

A catalog is a git repository. That is the whole distribution story in v1:

- The user configuration names one or more catalogs by URL and ref (tag,
  branch, or commit).
- Resolving a run writes the exact commit of each catalog into the lockfile;
  subsequent runs use the locked commits until the user explicitly updates.
- Catalogs are layered in declaration order: a later catalog can override
  frecklets, defaults, and curation policies of an earlier one. The intended
  shape is a small stack — an official curated catalog, optionally a personal
  catalog on top carrying private frecklets and local policy deviations.
  (The precise merge semantics — whole-frecklet replacement versus value-level
  override — is an open question for the spec.)

Because catalog content is pinned by commit and hashed into artifacts, a
catalog update is an ordinary, visible input change: the user bumps a ref,
freckles re-locks and re-renders, and the artifact diff shows exactly what
the update touches before anything is applied.

## 9. The execution journal

The journal is freckles' memory of its effects on the world. For every run of
an execute stage it appends: the stage identity, the hash of the artifact
consumed, the lockfile in effect, a timestamp, and the outcome (success,
failure, output summary). It is append-only and local to a deployment (with
room in the design for committing it alongside the configuration).

The journal answers the questions a template-based workflow cannot:

- *What is deployed?* The last successful journal entry per execute stage,
  with its artifact hash.
- *Is the deployment current?* Re-render (cheap, cached) and compare artifact
  hashes against the journal. A mismatch pinpoints which stages are stale.
- *What happened, and in what order?* The append-only history, hash by hash.

The journal deliberately does not duplicate tool state — no tfstate, no
kubeconfig contents. Those stay with their owners; the journal records
freckles-level facts only.

## 10. Worked example: rosekube as the first catalog

This walkthrough grounds every concept above in the existing rosekube stack.
It describes the target state, not current reality — today rosekube is a
Copier template, and this is what it looks like recast as a catalog.

**The catalog.** A git repository containing, among others:

- a `talos-cluster-proxmox` frecklet: contributes a render stage (transformer
  alias `copier`, pointing at what is today `templates/cluster/`'s
  opentofu/talos portion) and execute stages for VM provisioning and Talos
  bootstrap; declares pinned tools `tofu`, `talosctl`;
- a `flux-gitops` frecklet: render stage for the Flux layout, execute stages
  for pushing the repo and `flux bootstrap`; tools `flux`, `git`, `sops`,
  `age`;
- app frecklets (`paperless-ngx`, `linkwarden`, `karakeep`, `copyparty`,
  `harbor`, ...): each contributes its manifests/Helm defaults — today's
  `flux/catalog/<category>/<app>/` content with exact pinned versions — plus
  a configuration schema replacing today's overlay files;
- curation policies: PostgreSQL ⇒ app-local CloudNativePG cluster; ingress ⇒
  Tailscale-private by default; storage ⇒ default StorageClass (Longhorn)
  unless configured; every required-but-unfillable value surfaces in the
  user-config schema instead of a `CHANGE_ME` marker in a scaffold file.

**The user configuration.** Roughly the current `copier.yml` answers plus
app enablement — the things rosekube already identified as non-defaultable:

```yaml
catalogs:
  - url: https://codeberg.org/frkl/rosekube-catalog
    ref: v1

cluster:
  name: staging
  proxmox: { node: rose, endpoint: "https://rose.example.ts.net:8006/", vm_id: 501 }
  network: { bridge: vmbr5, cidr: 10.0.50.0/24, node_ip: 10.0.50.50, gateway: 10.0.50.1 }
  sizing: { cores: 4, memory_mib: 8192, system_disk_gib: 32, longhorn_disk_gib: 100 }
  git: { url: "ssh://git@codeberg.org/owner/staging-cluster.git", branch: main }

apps:
  paperless-ngx:
    enabled: true
    ingress: tailscale
  linkwarden:
    enabled: true

secrets:            # sops-encrypted values, ciphertext committed as-is
  proxmox_api_token: ENC[AES256_GCM,data:...]
  tailscale_oauth: { client_id: ENC[...], client_secret: ENC[...] }
```

Note what is absent: no overlay `kustomization.yaml` to uncomment, no
`_skip_if_exists` list, no scaffold files to fill in. Enabling Tailscale
ingress for Paperless is one line; the frecklet knows that this implies the
Tailscale operator (today a `depends_on` in overlay frontmatter) and pulls it
into the graph.

**The run.**

1. `freckles lock` resolves the catalog ref to a commit and every declared
   tool and transformer to an exact version; writes the lockfile.
2. `freckles render` evaluates the render stages: the `copier` transformer
   renders the cluster repository; app frecklets contribute their manifests;
   the result is one artifact — a complete, committable cluster repo — stored
   under its content hash. Re-running with unchanged inputs is a no-op.
3. `freckles apply` walks the execute stages as explicit checkpoints, each
   journaled with the artifact hash: push the rendered repo to the git
   remote; `tofu apply` (VM + Talos machine config — today's `just
   provisioning start` sequence: create VM, apply config, wait for the Talos
   API, health check); fetch kubeconfig; `flux bootstrap`. From there Flux
   reconciles the artifact's `flux/` tree, decrypting sops secrets
   in-cluster, exactly as rosekube does today.
4. Later, the user flips `karakeep: { enabled: true }` in the configuration.
   `freckles render` produces a new artifact whose diff against the journaled
   hash shows one changed area; the only stale execute stage is "push repo",
   and Flux does the rest.

**What improved over the template.** No hybrid file ownership — the rendered
repo is disposable and fully derived. The `just` recipe sequence became
declared, journaled execute stages. The tool-version prerequisites in
`check-tools.sh` became pinned, auto-provisioned, hashed tool dependencies.
And "which template version and answers produced this cluster?" has a
precise, machine-checkable answer.

## 11. Constraints and non-goals

Constraints (hard requirements):

- Runs on any Linux distribution; no distribution-specific packaging assumed.
- No root privileges for freckles itself; target-side privilege needs are
  rare, declared, optional, and explicitly confirmed.
- Python implementation, installable per-user (uv/pipx-friendly).
- Rendered output is never hand-edited; every customization has a home in
  the user configuration or a catalog layer.

Non-goals:

- **Not a Nix replacement.** No source-built hermetic toolchain, no global
  binary cache, no build sandbox. See
  [Reproducibility stance](#5-reproducibility-stance).
- **Not a configuration-management system.** freckles does not converge live
  systems; it renders artifacts and drives the tools (OpenTofu, Flux, Talos)
  that do.
- **Not a package manager.** The tool store serves freckles pipelines only;
  it does not manage the user's general environment.
- **Not multi-tenant orchestration.** One user configuration describes one
  deployment; fleet coordination is out of scope for v1.

## 12. Open questions

To be resolved by the specification:

1. **Stage declaration format.** The concrete schema by which frecklets
   declare stages, inputs, and transformer configuration — and how much of
   the DAG assembly is convention versus explicit wiring.
2. **Catalog layering semantics.** Whole-frecklet replacement vs. value-level
   merge when a personal catalog overrides an official one; how curation
   policies compose across layers.
3. **Transformer plugin interface.** The Python API and the purity contract
   (environment isolation, declared fetches, determinism testing); how
   third-party transformers are distributed and pinned.
4. **User-config schema definition.** How frecklets declare their
   configuration schema (types, requiredness, cross-frecklet references) and
   how schemas from many frecklets present as one coherent user surface.
5. **Journal storage and sharing.** Local file format; whether/how the
   journal is committed next to the configuration; multi-machine access.
6. **Artifact store layout.** On-disk format, garbage collection of old
   artifacts, and whether artifacts can be pushed/pulled between machines.
7. **Day-2 flows in detail.** Catalog update UX (re-lock, diff, selective
   apply), secret rotation, and how destructive changes (VM re-provisioning)
   are guarded.
8. **Rosekube migration.** The concrete path from the current Copier template
   and existing generated repositories to the first catalog release.

## 13. Roadmap to the spec

The specification grows next to this document under `docs/spec/`, in this
order — each part validated against the rosekube catalog before the next:

1. `spec/concepts.md` — normative glossary and data model (frecklet, catalog,
   stage, artifact, lockfile, journal), formalizing section 3.
2. `spec/pipeline.md` — stage graph assembly, hashing rules, caching, the
   render/execute contract (sections 4–5, open questions 1, 6).
3. `spec/catalog-format.md` — catalog repository layout, frecklet manifest
   schema, layering semantics (section 8, open questions 2, 4).
4. `spec/transformers.md` — plugin interface, purity contract, the initial
   transformer set: `copier`, `uv-python`, `pixi`, `command` (open
   question 3).
5. `spec/tools-and-secrets.md` — tool store, lockfile format, secrets flow
   (sections 6–7).
6. `spec/journal.md` — journal schema and currency semantics (section 9,
   open question 5).
7. `spec/rosekube-catalog.md` — the first catalog as a worked, testable
   instance of everything above (section 10, open questions 7, 8).
